wp2shell is the WordPress wake-up call.

A route-confusion bug and a type-handling mistake turn a stock WordPress install into an anonymous attack surface. The patch is available. The public exploit window is open. Here is what actually broke—and what to do next.

On 17 July, WordPress shipped an emergency security release for two Core vulnerabilities. In isolation, one is an SQL injection primitive and the other is a REST API routing flaw. Chained together, they can let an unauthenticated remote attacker move from a public HTTP request toward database access and remote code execution—without a vulnerable plugin being required.

The 30-second briefing

Upgrade first, investigate second. WordPress 6.9.0–6.9.4 and 7.0.0–7.0.1 are exposed to the full chain. Version 6.8.0–6.8.5 carries the SQLi component only. Fixed releases are 6.8.6, 6.9.5, and 7.0.2. Forced auto-updates were enabled, but defenders must verify—not assume—that every site completed the update.

01 / DISCLOSUREWhat happened—and what is confirmed

The official WordPress 7.0.2 release notice describes a “REST API batch-route confusion and SQL injection issue leading to Remote Code Execution.” The corresponding GitHub advisory rates the chain critical and names Adam Kues at Assetnote / Searchlight Cyber as the reporter.

The companion flaw, CVE-2026-60137, affects the author__not_in parameter in WP_Query. Its practical impact changes sharply when the REST routing flaw supplies data through a path that breaks the validation assumptions around it.

Precision matters: requests to the batch endpoint are not automatically malicious, and a public PoC is not evidence that a specific site was compromised. Treat those signals as investigation leads, not verdicts.

02 / ATTACK PATHTwo bugs, one dangerous chain

The weakness is best understood as a collapse of trust boundaries. One component assumes the REST layer delivered validated data. The route-confusion behavior undermines that assumption; the query layer then handles an unexpected scalar unsafely.

03 / CODE LEVELThe five lines that broke the boundary

Before the patch, normalization happened only when author__not_in was already an array. A scalar skipped the integer conversion, was later cast into an array, and then interpolated into SQL. The excerpt below is abridged from the public WordPress fix for clarity.

class-wp-query.php · vulnerable pattern
1if ( ! empty( $query_vars['author__not_in'] ) ) {
2  if ( is_array( $query_vars['author__not_in'] ) ) {
3    $query_vars['author__not_in'] =
4      array_map( 'absint', $query_vars['author__not_in'] );
5  }
6
7  $ids = implode( ',', (array) $query_vars['author__not_in'] );
8  $where .= " AND posts.post_author NOT IN ($ids) ";
9}
The scalar path bypassed absint(). This is a root-cause illustration, not an exploit payload.

The official patch normalizes every input shape at the point of use with wp_parse_id_list(). That turns acceptable IDs into integers and refuses to carry attacker-controlled SQL syntax into the query.

class-wp-query.php · patched pattern
1if ( ! empty( $query_vars['author__not_in'] ) ) {
2  $id_list = wp_parse_id_list(
3    $query_vars['author__not_in']
4  );
5
6  if ( count( $id_list ) > 0 ) {
7    sort( $id_list );
8    $where .= sprintf( ' ... NOT IN (%s) ',
9      implode( ',', $id_list ) );
10  }
11}
Source: WordPress commit 74d37a3. Excerpt abridged; consult the official diff.

Why this class of bug keeps happening

T

Type-dependent safety

Sanitization ran only for arrays. Security should not disappear when an unexpected scalar crosses the boundary.

↯

Validation far from use

The query layer trusted upstream REST validation instead of enforcing its own invariant where SQL was built.

⛓

Composable flaws

Moderate primitives become critical when one bug makes another bug reachable without authentication.

The durable engineering lesson is simple: normalize untrusted data at every trust boundary, then parameterize database operations. Route authorization, schema validation, and query safety should each survive independently when another layer fails.

05 / DEFENDER PLAYBOOKPatch, verify, then hunt

Do not wait for a perfect exploitability score. The operational facts—remote reachability, no authentication for the full chain, a Core component, an available patch, and public PoC code—already justify emergency handling.

  1. Inventory every WordPress origin Include campaign sites, staging hosts, forgotten subdomains, and externally managed properties—not just the primary domain.
  2. Upgrade to a fixed release Use 7.0.2 or the patched release for the maintained branch. Take a backup, but do not let a slow backup process create an unnecessary exposure window.
  3. Confirm the update completed Check the installed version at the origin. CDN cache, dashboard banners, and auto-update emails are not authoritative proof.
  4. Verify Core integrity Compare Core files against known-good checksums and review unexpected changes under plugins, themes, uploads, and web-root locations.
  5. Review identity and execution signals Investigate new administrators, password resets, plugin installations, scheduled tasks, PHP files in writable directories, and unusual outbound connections.
  6. Rotate secrets if compromise is suspected Reset WordPress salts, administrative credentials, database credentials, hosting control-plane access, deployment keys, and any secrets readable by the web process.

Checksum mismatches can have legitimate causes. Preserve evidence and investigate before deleting files.

High-value hunting pivots

Search web access logs for unusual bursts or malformed traffic involving /wp-json/batch/v1 and ?rest_route=/batch/v1, then correlate with database errors, authentication events, administrative changes, and file creation. A route hit alone is weak evidence; the surrounding sequence is what raises confidence.

If the vulnerable version was exposed before patching, treat version compliance as only the first step. A successful update closes the bug but does not evict an attacker who already created an administrator, implanted a plugin, or stole credentials.

06 / PATTERN MATCHPast incidents rhymed with this one

wp2shell is new, but its ingredients are not. Some of the most damaging web compromises started as a query primitive or a validation mismatch that became critical only when chained to another capability.

2018

Drupalgeddon 2 · CVE-2018-7600

Unsafe input handling in Drupal’s render pipeline enabled unauthenticated RCE and rapid mass exploitation. The recurring lesson: framework-level input assumptions have internet-scale consequences.

2022

WordPress SQLi · CVE-2022-21661

A WP_Query SQL injection flaw could become reachable through plugins or themes. The resemblance is architectural: a lower layer trusted callers to hand it safe values.

2023

MOVEit Transfer · CVE-2023-34362

An SQL injection path in an internet-facing application enabled broad data theft campaigns. Query access is rarely “just database read” once identity and application state are exposed.
